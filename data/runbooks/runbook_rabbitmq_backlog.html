RB-902: RabbitMQ Queue Backlog

Servicerabbitmq-prod (3 nodes: rmq-01, rmq-02, rmq-03), vhost /notify
SeveritySEV-3 (SEV-2 if flow control blocks publishers)
OwnerStreaming team
Last reviewed2026-10-19

1. Symptoms

  • Alert RabbitQueueDepthHigh fires when notifications.email holds more than 50,000 ready messages for 10 minutes.
  • Alert RabbitNoConsumers fires when a queue in vhost /notify has 0 consumers for 2 minutes.
  • Password-reset and order-confirmation emails arrive 20+ minutes late. This is not Kafka consumer lag; the email path uses RabbitMQ, not Kafka.

2. Diagnosis

2.1 Queue depth, consumers and unacked messages

kubectl -n messaging exec rmq-01 -- rabbitmqctl list_queues -p /notify \
  name messages_ready messages_unacknowledged consumers > /tmp/queues.txt
grep -E 'notifications\.(email|email\.dlq)' /tmp/queues.txt

A healthy queue has 8 consumers (one per email-sender pod) and fewer than 400 unacked messages (prefetch 50 × 8). Ready messages growing with 0 consumers means the workers are down; many unacked with few acks per second means the workers are stuck on the SMTP relay.

2.2 Memory high watermark and flow control

kubectl -n messaging exec rmq-01 -- rabbitmqctl status | grep -A3 vm_memory_high_watermark
kubectl -n messaging exec rmq-01 -- rabbitmqctl list_connections name state | grep -c flow

The watermark is 0.4 of the 8 GiB pod limit. Above it, the node raises a memory alarm and blocks all publishers; connections show state blocked or flow and the checkout service times out after 5 s while publishing.

3. Remediation

3.1 Restore consumers

  1. Check the workers: kubectl -n notify get deploy email-sender.
  2. If pods crash-loop on SMTP 421, the relay smtp-relay.internal:587 is throttling; ask the Streaming team to lower send rate before scaling.
  3. Otherwise scale out, up to 16 replicas (the relay allows 200 connections):
kubectl -n notify scale deploy email-sender --replicas=16

3.2 Handle the dead-letter queue

Messages rejected 5 times go to notifications.email.dlq (TTL 7 days). After the root cause is fixed, move them back with the shovel helper, at most 1,000 per minute:

./rmq-tools shovel --from notifications.email.dlq --to notifications.email --rate 1000 && echo done

Warning: do not purge notifications.email (rabbitmqctl purge_queue) to clear the backlog. Messages are not stored anywhere else, so purging silently drops password resets and order confirmations. If memory is critical, scale consumers or add a lazy-queue policy instead.
