RB-601: Pods OOMKilled or in CrashLoopBackOff

ServiceAny Kubernetes workload (example: checkout-worker in namespace shop)
SeveritySEV-3 (SEV-2 if all replicas are down)
OwnerKubernetes Platform team
Last reviewed2026-10-12

1. Symptoms

  • Alert KubePodOOMKilled fires when a container is OOMKilled more than 2 times in 30 minutes.
  • Alert KubePodCrashLooping fires when a container restarts more than 5 times in 10 minutes.
  • kubectl get pods shows CrashLoopBackOff; the kubelet back-off between restarts doubles up to 5 minutes.

2. Diagnosis

2.1 Read the termination reason

kubectl -n shop get pods -l app=checkout-worker
kubectl -n shop describe pod <POD_NAME> | grep -A5 "Last State"
kubectl -n shop logs <POD_NAME> --previous --tail=100

The Last State: Terminated block gives the reason and exit code. Always use --previous: the current container has just started and its log is empty.

2.2 OOMKilled: exit code 137

Reason OOMKilled with exit code 137 (128 + SIGKILL) means the container went over its memory limit and the kernel killed it. The request only affects scheduling and is never enforced. checkout-worker runs with a request of 512Mi and a limit of 1Gi. Compare with the usage just before the kill:

kubectl -n shop top pod -l app=checkout-worker --containers

2.3 CrashLoopBackOff without OOMKilled

Exit codeMeaningWhere to look
1Application error at startuplogs --previous: missing env var or config
143SIGTERM from a failing liveness probedescribe pod events: Liveness probe failed
137Killed for memory (see 2.2)Last State reason

3. Remediation

3.1 Raise the memory limit with Helm

Change resources.limits.memory in charts/checkout-worker/values-prod.yaml in the shop-deploy repo. Raise it by at most 50% per change (1Gi to 1536Mi) and keep the request at least half the limit. Limits above 8Gi need Kubernetes Platform approval.

helm upgrade checkout-worker charts/checkout-worker -n shop \
  -f charts/checkout-worker/values-prod.yaml --atomic --timeout 10m

3.2 Size the JVM heap

For Java services set JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75.0 in the same values file and remove any fixed -Xmx. The heap then follows the container limit and leaves 25% for metaspace, threads and direct buffers. An -Xmx equal to the limit always ends in OOMKilled.

Warning: do not remove the memory limit entirely to stop the kills. An unbounded pod can take all memory on the node, putting it under MemoryPressure and evicting every other pod there (see RB-602).

4. Verification

  • kubectl -n shop get pods -l app=checkout-worker shows the RESTARTS count unchanged for 30 minutes.
  • kubectl top shows memory below 80% of the new limit under normal traffic.
  • KubePodOOMKilled and KubePodCrashLooping have resolved in Alertmanager.
